Plano de Correção do PortfolioLab

Os 24 achados da auditoria organizados em cinco ondas, na ordem em que precisam ser atacados. Cada correção começa por um teste que falha. Um branch e um PR por onda.

A ordem não é negociável e é o ponto principal deste documento

A tentação é começar pelos quatro achados críticos, porque são os que quebram a regra de negócio. Seria um erro. Dois achados de severidade alta são portas: enquanto estiverem abertos, qualquer correção feita depois é insegura de verificar.

O achado 7 — a suíte escreve no banco de produção — significa que hoje você não pode rodar testes com tranquilidade. Como as 24 correções vão ser verificadas por teste, isolar o banco é literalmente o primeiro passo possível. O achado 5 — não existem migrations — bloqueia o achado 9, que exige mudança de schema. Sem histórico versionado, alterar o banco vira db push na produção, às cegas.

Há ainda dois pares que precisam ser corrigidos juntos, porque um cria a condição para o outro. O diagrama abaixo mostra as dependências reais.

Grafo de dependências por que esta ordem

As duas descobertas que reorganizam o trabalho leia antes de começar

Os achados 2 e 3 são o mesmo problema visto de dois lados. Hoje a tela de metas oferece um seletor alimentado por GET /assets — e é justamente por isso que a rota precisa devolver o catálogo global, vazando os tickers de todo mundo. Quando o achado 2 for corrigido e as metas aceitarem qualquer ticker da B3, o seletor deixa de ser necessário: vira um campo de busca igual ao que já existe em nova-transacao.tsx. Só então GET /assets pode ser reduzido aos ativos do próprio usuário sem quebrar a interface. Corrigir o 3 sozinho, antes, deixaria a tela de metas inutilizável.

Os achados 1 e 12 têm a mesma causa raiz. A corrida da simulação só existe porque quotesService grava preço no meio de uma requisição de leitura, numa tabela global. Não adianta reordenar o Promise.all e deixar a escrita onde está: a próxima rota que ler preço em paralelo reintroduz o mesmo defeito. A correção é resolver os preços uma vez, num mapa explícito, e passá-lo adiante.

Pré-requisito de máquina Não há Docker, Postgres nem psql instalados aqui — o docker-compose.yml do repositório nunca foi executado nesta máquina. A Onda 0 começa pela instalação do Docker Desktop, e nada mais pode ser verificado antes disso.

00

Fundação: banco de teste e migrations

onda-0-fundacao

Nenhuma linha de regra de negócio é tocada nesta onda. O objetivo é único: tornar possível verificar tudo o que vem depois.

Achado 7Isolar a suíte do banco de produção

Teste primeiro
Um teste do próprio guarda: afirma que a função de proteção lança quando recebe uma DATABASE_URL apontando para pooler.supabase.com e passa quando aponta para localhost. É o único teste do projeto cujo trabalho é proteger o projeto de si mesmo.
Correção
Criar backend/.env.test com a URL do container. Em vitest.config.ts, carregar esse arquivo e injetar via test.env — o Vitest define process.env antes de os módulos de teste carregarem, e o dotenv/config de config/env.ts não sobrescreve variável já existente, então o valor do teste vence. Somar um globalSetup que aborta a suíte inteira se a URL não for local, e o mesmo guarda no topo de prisma/seed.ts. 
// vitest.config.ts  ->  globalSetup
if (!/localhost|127\.0\.0\.1/.test(process.env.DATABASE_URL ?? "")) {
  throw new Error(
    "Suite abortada: DATABASE_URL nao aponta para um banco local. " +
    "Veja a skill rodar-testes-seguro."
  );
}
Pronto quando
npm test passa contra o container e os 54 testes continuam verdes; npm run db:seed com a URL do Supabase é recusado com mensagem clara; backend/.env.test está no .gitignore.

Achado 5Criar o histórico de migrations e alinhar a produção

Teste primeiro
Aqui a verificação não é um it(), é um comando: prisma migrate status deve reportar pendência antes e limpeza depois, nos dois bancos. Colar a saída no PR como evidência.
Correção
Gerar a migration inicial a partir do schema atual e, na produção — que já tem o schema aplicado via db push —, marcá-la como aplicada sem reexecutar. É o fluxo de baselining do Prisma, e a ordem importa: 
# 1. gerar o SQL da migration inicial (nao aplica nada)
mkdir -p prisma/migrations/0_init
npx prisma migrate diff \
  --from-empty --to-schema-datamodel prisma/schema.prisma \
  --script > prisma/migrations/0_init/migration.sql

# 2. no banco LOCAL: aplicar de verdade
npx prisma migrate dev

# 3. na PRODUCAO: marcar como ja aplicada, sem reexecutar
#    (DATABASE_URL apontando para o Supabase apenas nesta linha)
npx prisma migrate resolve --applied 0_init
Fechar atualizando README.md e docs/deploy.md, que hoje recomendam db push para mudanças futuras.
Pronto quando
prisma/migrations/0_init/ versionado; migrate status limpo no local e na produção; o item “Rodar a primeira migration” do Sprint 1 finalmente marcável no roadmap.

Onda 1 — A regra de negócio os quatro achados críticos

01

Consertar o que o produto promete fazer

onda-1-regra-de-negocio

A onda mais importante e a mais delicada. Três dos quatro achados estão em módulos sem nenhum teste hoje — cada correção nasce acompanhada da sua cobertura.

Achados 2 + 3Metas de qualquer ticker, catálogo por usuário

Teste primeiro
Dois testes de integração: PUT /goals com um ticker que o usuário nunca negociou responde 200 e cadastra o ativo; e o usuário B não encontra em GET /assets um ticker que só o usuário A negociou. Ambos falham hoje.
Correção
Em goals.service.ts:23 e dividends.service.ts:8, trocar assetsRepository.findByTicker por quotesService.buscarOuCadastrar — a mesma função que transactions.service.ts:10 já usa. A mensagem de erro passa a ser “não encontrado na B3”, coerente com transações. Em seguida, assetsRepository.findAll ganha userId e devolve só os ativos em que o usuário tem transação, meta ou provento. No frontend, simulacao/page.tsx troca o <select> pelo campo de busca com /quotes/:ticker que nova-transacao.tsx já implementa, inclusive o atraso de 500 ms.
Pronto quando
Uma conta recém-criada consegue montar a carteira-alvo inteira antes de comprar o primeiro ativo, e nenhuma rota devolve ticker de outro usuário.

Achados 1 + 12Um preço só por ativo, resolvido uma vez

Teste primeiro
Teste unitário da nova função de resolução de preços, e um teste de integração em que o preço gravado no banco difere do preço vivo: a quantidade sugerida precisa bater com o preço vivo. Com o código atual, ele falha por usar o preço do banco.
Correção
Três mudanças que só funcionam juntas. Primeiro, goalsRepository.findManyByUser passa a trazer priceUpdatedAt no select — hoje traz apenas ticker, name, type, currentPrice, e sem esse campo não há como saber se o preço está velho. Segundo, rebalanceService.simulate deixa de ler m.asset.currentPrice: carrega metas e carteira, monta a união dos ativos, faz uma chamada de resolução de preços e usa o mapa resultante tanto para precoAtual quanto para valorAtual. Terceiro, o prisma.asset.update sai de quotes.service.ts para um quotes.repository.ts novo — onde deveria estar desde sempre, e que o agente revisor-camadas aponta como violação de camada.
Pronto quando
Nenhum asset.currentPrice é lido dentro de rebalance, nenhum prisma. aparece fora de um *.repository.ts, e o agente auditor-financeiro roda sobre o módulo sem achados.

Achado 4Impedir que apagar uma transação corrompa a posição

Teste primeiro
Compra 100 → venda 100 → DELETE da compra deve responder 409 e deixar a posição intacta. Hoje responde 204 e deixa −100 no banco.
Correção
calcularPosicao passa a devolver também quantidadeMinima — o menor valor que a quantidade atinge ao longo da sequência cronológica. É uma linha a mais no laço que já existe, e mantém a função pura e testável. transactionsService.remove então carrega as transações daquele ativo, simula a remoção e recusa com 409 se quantidadeMinima ficar negativa, explicando qual venda posterior ficaria descoberta.
Pronto quando
Não existe sequência de operações pela API que produza quantidade negativa, e o filtro quantidade.lte(0) em getCarteira volta a significar apenas “posição zerada”, não “dado corrompido escondido”.

Onda 2 — Segurança e integridade achados 6, 8, 9, 16

02

Fechar as portas antes de publicar

onda-2-seguranca

Nenhum destes quebra a aplicação hoje. Todos quebram no dia em que ela sair do localhost — que é a última linha aberta do roadmap.

Achado 6JWT_SECRET sem valor padrão em produção

Teste primeiro
Validar o schema de ambiente com NODE_ENV=production e o segredo padrão deve lançar; com development, deve passar.
Correção
Manter o .default() para não criar atrito no desenvolvimento, mas acrescentar um superRefine que rejeita, em produção, segredo ausente, igual ao padrão, ou com menos de 32 caracteres. O comentário no topo do arquivo promete fail fast — a mudança faz o código cumprir a própria promessa.
Pronto quando
A API se recusa a subir em produção sem segredo forte, com mensagem dizendo como gerar um.

Achado 8Teto de requisições e cota de relatórios

Teste primeiro
Tentativas repetidas de login passam a receber 429 depois do limite; o usuário que excede a cota de relatórios recebe 429 com mensagem própria.
Correção
express-rate-limit (8.6.2) em três camadas: rígida em /auth/login e /auth/register por IP; por usuário em POST /reports e /reports/:id/ask, que custam dinheiro real de API; e um teto global folgado. Somar uma cota de relatórios armazenados por usuário, verificada em reportsService.analisar.
Detalhe que costuma passar batido Atrás de Render ou Vercel é preciso app.set("trust proxy", 1). Sem isso todos os IPs viram o do proxy, e o limite que deveria ser por visitante passa a valer para a aplicação inteira de uma vez.
Pronto quando
Força bruta em /auth/login é barrada e não há caminho para esgotar a cota do Gemini pela API.

Achado 9onDelete explícito nas chaves estrangeiras

Teste primeiro
Apagar um usuário com transações, metas, proventos e relatórios deve funcionar em cascata; apagar um Asset que alguém possui deve continuar falhando.
Correção
Migration acrescentando onDelete: Cascade nas relações que apontam para User e onDelete: Restrict explícito nas que apontam para Asset. A segunda metade não é redundância: torna intencional o que hoje é só o padrão do Prisma. Como efeito colateral, o afterAll de portfolio.api.test.ts deixa de precisar apagar transações na mão.

Depende da Onda 0 — sem migrations não há como aplicar isso com segurança.

Pronto quando
A migration está versionada, aplicada nos dois bancos, e a limpeza manual saiu dos testes.

Achado 10Parar de descartar a taxa de venda

Teste primeiro
Compra com taxa e venda com taxa: o preço médio deve continuar inalterado pela venda (isso já está correto hoje) e a taxa da venda deve aparecer no total de custos.
Correção
calcularPosicao passa a acumular taxasPagas nos dois sentidos, e getSummary expõe totalTaxas.
Escolha deliberada, e vale discordar O caminho mais “correto” segundo a Receita seria apurar ganho de capital realizado, descontando a taxa da venda. Mas o lucroTotal de hoje é ganho não realizado (patrimônio menos aplicado), e misturar os dois produziria um número que não significa nada. Expor as taxas separadamente resolve o problema real — o dinheiro deixa de ser invisível — sem inventar uma apuração que ninguém pediu. Se a apuração de ganho realizado entrar depois, já encontra o dado disponível.

Como cada onda entra no repositório o mesmo ritual, cinco vezes

Branch a partir da main, teste que falha, correção, teste verde, PR descrevendo os achados que a onda fecha. O PR referencia os números da auditoria, de modo que o histórico do repositório e o relatório contem a mesma história. 

git switch -c onda-1-regra-de-negocio
# por achado:  teste que falha  ->  correcao  ->  teste verde
cd backend && npx tsc --noEmit && npm test
git push -u origin onda-1-regra-de-negocio
gh pr create --title "Onda 1: regra de negocio (achados 1, 2, 3, 4, 12)"

Duas skills do projeto valem ser acionadas em toda onda: rodar-testes-seguro antes de qualquer npm test, e auditar-calculo-financeiro em qualquer mudança que toque dinheiro. Os agentes auditor-financeiro e revisor-camadas entram antes de abrir o PR — são somente leitura, então não alteram nada: apontam.
